Architecture walkthrough

QuadERP — how the app works

A multi-tenant retail ERP: one React app serving many businesses, an Express API that does the enforcing, and a Postgres database that owns the invariants. This traces a request through all three.

01 The shape of it

Three tiers, three hosts. The browser gets a React 19 SPA built by Vite and served from Vercel; it is a PWA, so it installs a service worker and keeps a local IndexedDB cache. The API is Express 5 on Railway, started through cluster.js so several worker processes share the port. The data lives in Supabase Postgres, reached by the server with a service-role client and protected by row-level security.

Tenancy is carried by the hostname. quaderp.app is the marketing site — a separate deployment. The ERP is one level down at app.quaderp.app, and each business nests under that, so acme.app.quaderp.app shows a login page branded for Acme. The slug is resolved client-side by lib/subdomain.js, which deliberately refuses to read a slug out of any host that is not the configured base domain — Vercel preview URLs and localhost can never be mistaken for a tenant.

02 One request, end to end

Every read and write in the app follows the same seven steps. Pages never call fetch themselves: they call a hook, the hook calls lib/api.js, and that one module is where the Supabase JWT gets attached.

03 Two gates, and only one of them counts

Permissions are checked twice, against the same strings, for two different reasons. In the browser, ProtectedRoute wraps each route and swaps the page for an Access denied screen — that is a courtesy, so nobody navigates into a dead end. At the API, permissionCheck returns 403 — that is the part an attacker cannot skip.

04 A sale, the app's busiest write

A sale is not one insert. It creates the sale and its line items, decrements stock for every product sold, and posts to the ledger — and a till that is short by one unit is a real accounting problem, so those cannot half-happen. The server hands the whole thing to a single Postgres function, process_sale_transaction, and lets the database make it atomic.

Shops lose connectivity, so the register keeps working without it. When the browser goes offline the sale is written to an IndexedDB queue instead, and OfflineStatus drains that queue through a dedicated sync endpoint once the connection returns.

05 What runs without anyone asking

Two schedulers run inside the API process. subscriptionCron fires daily at midnight to advance billing and subscription state; webhookRetryCron sweeps every five minutes and re-attempts webhook deliveries that failed. Outbound integrations go through webhookDispatcher, and third-party storefronts come in through a separate public API guarded by an API key rather than a user session, rate limited to 120 requests a minute per business — keyed on the tenant rather than the IP, because several storefront requests can legitimately share one address.

The schema is versioned as 64 numbered migrations applied by store-app/server/db/migrate.js. DDL runs over a direct Postgres connection, not the Supabase JS client, which cannot issue it.

07 Measured, not estimated

All 40 pages were loaded against a production build — vite build, served by vite preview, not the dev server, whose unbundled module graph would say nothing useful. Each route got its own full document navigation, so every number below describes that page's own load rather than a client-side transition.

The app is a PWA, and that splits the story in two. A first visit pulls the bundle over the network; every visit after that is served by the service worker from a 2.2 MB precache, which is why the warm column reports zero bytes transferred.

What the run found

Zero console errors and zero uncaught exceptions across all 80 captures. One route redirects by design — /products forwards to /inventory. The two public pages are measured separately: mock mode hands the app a signed-in session, so /login bounces to the dashboard and can only be captured against a build with mocks switched off.

The dashboard is the outlier and it is the honest one to look at: heaviest first paint (540 ms) and by far the slowest to settle (2,485 ms), because it mounts four Recharts visualisations whose entry animations run for 1.5 s. The point of sale is second, and for a different reason — 19 requests, the most of any page.

One real defect, and it is in the test data

The Accounts Receivable ledger renders $NaN in its Amount and Outstanding columns. The page is fine; the fixture is stale. Migration 056 renamed ar_invoices.amount to total_amount, and BillingLedgerView reads total_amount and amount_paid — but the mock fixture still supplies the pre-056 amount and balance, so both operands come back undefined and the subtraction yields NaN.

Worth fixing for a reason beyond the screenshot: the committed visual baseline for that route has $NaN baked into it, so the suite is currently green on a page rendering garbage.

What these numbers do not include. The run drives the app's mock harness, so every API call is answered from a local fixture instead of Railway and Supabase. That makes the comparison between pages fair and repeatable, and it means these are front-end figures — bundle, render and paint — not end-to-end latency. Real API time sits on top of every number here.
